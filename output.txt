## 1

1. 本書について
1.1. 本書の位置付けと目的
本書の目的は、単体テストのテスト方針および観点を明確にし、アプリケーションプログラマごとの品質のばらつきを抑制することである。
本書では、本プロジェクトにおける単体テスト方針、単体テスト実施範囲、単体テスト観点に関して記述する。
なお、本書で記述する単体テスト観点は最低限考慮すべき観点である。
機能によって追加で確認が必要な観点があれば追加してテストを実施すること。
1.2. 参照ドキュメント
本書では以下のドキュメントに依拠してテスト方針、観点を策定している。
・テスト観点カタログ
・テスト種別カタログ
いずれも次のURLより入手可能である。必要に応じて参照すること。
https://fintan.jp/page/1456/

2.3. 単体テスト実施環境
単体テストは開発者ローカルPC上に構築する開発環境上で実施する。
2.3. 単体テスト終了条件
単体テストの終了条件は以下の通りとする。
・ クラス単体テスト、リクエスト単体テスト合わせて、カバレッジのC0（命令網羅）、C1（条件網羅）が100%であることを確認すること。
カバレッジが100%に到達しない場合は、その理由を明確にして問題がないことを確認する。
ただし、Formクラスのアクセサについてはカバレッジが100%にならないとしても、問題なしとする。
(Formの場合はリクエスト単体テストで通過しないsetterはどこからも呼ばれることが無いため、通過していなくても問題なしとする)
・ すべての単体テストケースが実施済みであり、結果がすべて合格であること。
・ 単体テスト結果レビューにおける指摘事項がすべて修正済みであり、確認結果が合格であること。

## 3

3. 単体テスト概要
3.1. 単体テスト仕様書作成単位
1つのシステム機能設計書あるいは共通コンポーネント設計書に対し1つの単体テスト仕様書を作成する。
単体テスト仕様書には、該当取引に含まれるクラス単体テストケース、リクエスト単体テストケース、取引単体テストケースを記述する。
※リクエスト単体テストごとにテスト仕様書を作成すると、総合的にテストケースが十分かの確認がしづらいためである。
なお、Formクラスの単体テストについては、クラス単体テストケースで網羅性の確認を行えるため、単体テスト仕様書は作成しない。
また、クラス単体テストおよびリクエスト単体テストの単体テスト仕様書の作成要否については、アーキテクトの指示に従うこと。
3.2. 単体テスト観点概要
本プロジェクトにおける単体テスト仕様書フォーマットは、テスト観点カタログと単体テスト標準に基づいて作成されている。
これに業務的なテスト観点を追加してテスト仕様書を作成する。
個別の業務要件
テスト仕様書フォーマットには、テスト種別ごとに以下のシートが用意されている。
・クラス単体テスト
・リクエスト単体テスト
・取引単体テスト
このうち、クラス単体テストとリクエスト単体テストは、テスト観点カタログに記載されているテスト観点を元にして作成している。
以下に、クラス単体テストとリクエスト単体テストのシートと、元になったテスト観点カタログのシートとの対応を示す。
処理方式: 画面 / シート: クラス単体テスト / 元となったテスト観点カタログのシート: 機能テスト【共通】
シート: リクエスト単体テスト / 元となったテスト観点カタログのシート: 機能テスト【共通】、機能テスト【ウェブアプリケーション】
処理方式: REST / シート: クラス単体テスト / 元となったテスト観点カタログのシート: 機能テスト【共通】
シート: リクエスト単体テスト / 元となったテスト観点カタログのシート: 機能テスト【共通】、機能テスト【ウェブサービス】
処理方式: バッチ / シート: クラス単体テスト / 元となったテスト観点カタログのシート: 機能テスト【共通】
シート: リクエスト単体テスト / 元となったテスト観点カタログのシート: 機能テスト【共通】、機能テスト【バッチアプリケーション】

テスト仕様書フォーマットの観点は、テスト観点カタログに記載のものを全て転記している。
しかし、処理方式・テスト種別によってテストが不要と判断できるものに関しては、あらかじめ項目をグレーアウトしている。
あらかじめグレーアウトしている項目については、不要と判断した理由を「対象外理由」列に記載している。
業務的なテスト観点に照らして個別にテスト不要と判断できるものがある場合は、項目をグレーアウトしたうえで「テスト内容」列に
不要と判断した理由を記載すること（あらかじめグレーアウトされているものと区別できるようにするため）。
取引単体テストについては、独自に検討したテスト観点を元にして作成している。
テスト観点の詳細については後述する。

4.1.2. テスト観点詳細
(1)取引実行確認
取引全体を通して、仕様通りに取引内の処理が実行されることを確認する。
(1-2)画面遷移パターン
画面遷移パターンごとに、取引が仕様通りに実行されることを確認する。
また、各画面での表示内容および画面間でのウィンドウスコープやhiddenタグを使用した情報の引継ぎが仕様通りに行われていることを確認する。
取引を通して正常に処理が実行されていることを確認するために、各リクエストでの処理結果（画面ダンプ、DBダンプなど）を取得する。
(1-2-1)正常取引
エラーや戻るイベントが発生せずに取引を完了する画面遷移パターン。
<<画面遷移パターンの例>>
取引: 検索取引 / 画面遷移の例: 一覧照会（検索） / → / 一覧照会（結果） / → / 詳細表示
取引: 登録取引 / 画面遷移の例: 登録 / → / 登録確認 / → / 登録完了 / → / 一覧照会
取引: 更新取引 / 画面遷移の例: 更新 / → / 更新確認 / → / 更新完了 / → / 一覧照会
取引: 削除取引 / 画面遷移の例: 削除確認 / → / 削除完了 / → / 一覧照会

(1-2-2)戻るイベント
取引の画面遷移中に、戻る処理を含む画面遷移パターン。
<<画面遷移パターンの例>>
### 取引

検索取引: 登録取引 / 一覧照会（検索）: 登録 / →: → / 一覧照会（結果）: 登録確認[※戻る] / →: ⇒ / 詳細表示[※戻る]: 登録
検索取引: 更新取引 / 一覧照会（検索）: 更新[※戻る] / →: ⇒ / 一覧照会（結果）: 詳細表示 / →: → / 詳細表示[※戻る]: 更新 / ⇒: → / 一覧照会（結果）: 更新確認[※戻る] / ⇒ / 更新
検索取引: 削除取引 / 一覧照会（検索）: 削除確認[※戻る] / →: ⇒ / 一覧照会（結果）: 詳細

(1-2-3)検索結果0件
一覧検索などの検索処理を行う取引で、検索結果が0件となった場合を含む画面遷移パターン。
(1-2-4)サブウィンドウ連携
取引の画面遷移中に、サブウィンドウでの処理の実行を含む画面遷移パターン。
特に、サブウィンドウの開閉時に親ウィンドウとサブウィンドウ間での情報の連携が正しく行われているかどうかについても
検証を行うこと。
(1-2-5)異常取引
取引の画面遷移中に、以下のようなエラーが発生する場合を含む画面遷移パターン。
・ 精査エラー
・ 検索結果上限超過エラー
・ 排他制御エラー
上記以外にも、業務的に発生しうるエラーが存在する場合には、それらのエラーが発生するパターンについても確認する。
<<画面遷移パターンの例>>
取引: 検索取引 / 画面遷移の例: 一覧照会（検索） / → / 一覧照会[※エラー] / ⇒ / 一覧照会（結果） / → / 詳細表示
取引: 登録取引 / 画面遷移の例: 登録 / → / 登録[※エラー] / ⇒ / 登録確認 / → / 登録完了
取引: 更新取引 / 画面遷移の例: 更新 / → / 更新[※エラー] / ⇒ / 更新確認 / → / 更新完了

※通常、削除取引でエラーが発生するケースは処理の継続が行えないが、設計書に処理継続の仕様があればテストを行うこと。
(1-2-6)その他イベント
取引の画面遷移中に、一覧検索結果のページングやソートなど、上記以外のイベントを含む画面遷移パターン。
(1-2-7)複数の画面遷移パターンの組み合わせ
上記の画面遷移パターンを組み合わせた場合にも、取引が仕様通りに実行されることを確認する。
